\section{Methodology}
\label{sec:methodology}

\paragraph{Experimental matrix.}
We evaluate $5$~models $\times\,6$~domains $\times\,2$~prompting conditions
$=60$ cells, with $10$~problem instances per cell on the simple-tier
domains and $20$ per cell on the complex tier ($871$ executed instances
in total). All planning problems use the PDDL formal-planning
language~\cite{pddl}, and all generated plans are checked by an
external classical validator --- the \emph{LLM-Modulo} architecture
recommended by Kambhampati et al.~\cite{kambhampati2024llmmodulo}, in
which the LLM proposes plans and a sound external module accepts or
rejects them. The matrix was rolled out incrementally: a 3-model core
slate (Llama-3.1-8B, Qwen2.5-32B, Llama-3.3-70B) on three complex domains
(\texttt{blocksworld}, \texttt{citycar}, \texttt{tetris}) was first
executed to validate the design, then extended in two waves: two more
models (QwQ-32B for a reasoning-post-training ablation, Mistral-Small-24B
for a third-family cross-check), then three simple short-plan domains
(\texttt{basic\_move}, \texttt{visit-all}, \texttt{satellite}) that
serve as a difficulty floor and pipeline check. The design commitment
is that the only thing varying between two cells is the axis under
study (model, domain, or prompting condition); everything else is
controlled by a single \texttt{config.yml} loaded once per job.

\paragraph{Models.}
The five-model slate spans three families and roughly one order of
magnitude in parameter count: Meta (Llama-3.1-8B in bf16,
Llama-3.3-70B in 4-bit NF4), Alibaba (Qwen2.5-32B and QwQ-32B, both
bf16), and Mistral (Mistral-Small-24B, bf16). QwQ-32B is the same base
architecture as Qwen2.5-32B with reasoning post-training added,
isolating the post-training axis. Llama-3.3-70B was loaded in 4-bit
NF4 (\texttt{bitsandbytes}) to fit on $2 \times$ A100-64\,GB; the
quantization confound is discussed in Section~\ref{sec:limitations}.

\paragraph{Prompts.}
The two source projects each shipped a monolithic per-domain prompt;
we replaced this with a three-file module under
\texttt{src/prompts/}: \texttt{shell.py} (system prompt,
chain-of-thought scaffold, validation-feedback template),
\texttt{descriptions.py} (one verbatim natural-language description per
active domain), and \texttt{compose.py} (the \emph{model-agnostic}
\texttt{build\_problem\_prompt(domain, condition, pddl\_domain,
pddl\_problem)} entry point). Because the composer takes no model
argument, byte-identity of prompts across models is a structural
property rather than a runtime invariant. The two prompting conditions
differ only in the \texttt{cot} scaffold prepended to the description.

\paragraph{Generation configuration.}
All cells use the same sampling configuration: \texttt{temperature=0.1},
\texttt{top\_p=0.95}, \texttt{top\_k=10}, \texttt{seed=42},
\texttt{max\_new\_tokens=8192} for the bf16 models and $16384$
for QwQ-32B (whose long \texttt{<think>} traces, characteristic of
zero-shot CoT-style reasoning~\cite{kojima2022zeroshot}, fill the
smaller budget; see Section~\ref{sec:limitations}). At job start, the
generation configuration is echoed to stdout as a canonical JSON line;
\texttt{grep}-ing the line across all stdout files gives a post-hoc,
byte-exact audit of generation-config uniformity.

\paragraph{Iteration policy.}
Each instance gets up to four attempts under a stop-on-success policy
inspired by self-refinement work~\cite{madaan2023selfrefine}:
prompt the model, write the iteration's plan to disk, run VAL with the
verbose flag, parse VAL's output into a metrics row, and break out of
the loop on first valid plan. If all four attempts fail, the
final plan file records \texttt{first\_valid\_iter = null}. Every
iteration is logged before the validity check, so failed attempts are
preserved for iteration-gain analysis. The price of stopping early is
a well-understood selection bias: iterations $2$--$4$ contain only
instances that failed earlier, so per-iteration aggregates across cells
are not directly comparable without conditioning on
``reached iter $k$''. Cumulative-solve curves
(Figure~\ref{fig:plot3}) avoid this by indexing on per-instance
first-valid iteration instead.

\paragraph{Validator and metrics.}
Plans are validated with the KCL-Planning VAL toolkit (verbose mode);
a thin wrapper in \texttt{src/utils/validator.py} returns
\texttt{(is\_valid, raw\_stdout)}, and
\texttt{src/utils/metrics\_extractor.py} parses VAL's stdout into the
schema \texttt{(plan\_text, plan\_len, solves\_problem,
valid\_action\_percent, consecutive\_valid\_steps,
logical\_violations, wallclock\_s, prompt\_tokens, completion\_tokens)}.
A single validator and a single parser, called from a single point in
the iteration loop, provide one source of truth for every metric in
Section~\ref{sec:results}.

\paragraph{Ground-truth difficulty.}
For four of the six domains we computed an optimal-or-near-optimal
plan length per instance with the classical
\texttt{pyperplan}~\cite{pyperplan} planner
(A*+\texttt{hff} for \texttt{blocksworld}; BFS for \texttt{basic\_move}
and \texttt{visit-all}; hand-curated reference from Fast Downward for
\texttt{satellite}, which uses \texttt{:equality} that pyperplan
cannot parse). The original PDDL instances follow the IPC
benchmark conventions and are sourced from the public
\texttt{potassco/pddl-instances} collection~\cite{ipc-instances}. \texttt{citycar} and \texttt{tetris} use
\texttt{:functions} (numeric fluents) and have no ground-truth column.
The reference data lives in
\texttt{src/data/<domain>/REFERENCE\_PLANS.csv} and is loaded by the
analysis notebook to produce Figures~\ref{fig:plot13}
and~\ref{fig:plot15}.

\paragraph{Reproducibility.}
The full experimental log (every per-iteration row, every plan, every
SLURM stdout) lives under \texttt{src/results-final/}. Every figure
and table in the next section is regenerated end-to-end by
\texttt{notebooks/results\_analysis.ipynb} from those CSVs; the SLURM
entry script \texttt{scripts/slurm/run.sh} is parametric over
\texttt{(MODEL, DOMAIN, CONDITION)} and enforces the
single-config-source-of-truth invariant.
