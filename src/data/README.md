# PDDL Data — Domain & Instance Layout

Each subdirectory under `src/data/` is one PDDL planning domain. Drop a folder here
with the right files and the harness will discover it automatically.

This document is the **authoritative contract** for adding a new domain.
If something here disagrees with code, the code wins — please open a PR to fix the doc.

---

## File-naming contract

The rule is intentionally simple — **any `*.pddl` file whose name contains
"domain" (case-insensitive) is the domain file; every other `*.pddl` file in
the folder is treated as a problem instance.** No specific filename is required.

| File | Required? | What counts |
|---|---|---|
| Domain file | **Yes** (exactly one) | Any `*.pddl` whose name contains "domain". Examples: `domain.pddl`, `<dirname>_domain.pddl`, `city_car_domain.pddl`. When several match, the loader prefers `domain.pddl`, then `<dirname>_domain.pddl`, then the lexicographically first match. |
| Problem instances | **Yes (≥1)** | Any other `*.pddl` file. Canonical: `instance-NN.pddl`. Legacy `problem_NN.pddl` / `prob*.pddl` work just as well. |
| `REFERENCE_PLANS.csv` | Optional | Generated by [`scripts/verify/validate_instances.py`](../../scripts/verify/validate_instances.py); only used by the analysis notebook. |
| `README.md` | Optional | Per-domain notes (sources, IPC year, gotchas). |

The auto-discovery logic lives in [`src/core/file_manager.py`](../core/file_manager.py)
(`_locate_domain_file` and `_collect_problem_files`) and is mirrored exactly in
[`scripts/verify/validate_instances.py`](../../scripts/verify/validate_instances.py).
The instance stem (e.g. `instance-01`, `problem_01`) flows through to `--instance`
on the CLI, to per-iteration filenames in `src/results/`, and to the `instance`
column of `run_metrics.csv`.

## Active vs available

`config.yml` has two lists:

```yaml
domains:
  active:    [blocksworld, citycar, tetris, basic_move, visit-all, satellite]
  available: [blocksworld, citycar, tetris, basic_move, visit-all, satellite,
              folding, gripper, hanoi, labyrinth, logistics, monkey, shoe-sock, travel]
```

- `available` — every name that `--domain <name>` will accept.
- `active` — what `scripts/slurm/submit_all.sh` and `validate_instances.py` iterate over by default.

Domains in `available` but not `active` are **dormant** — their PDDL files are present
but they have no natural-language description in [`src/prompts/descriptions.py`](../prompts/descriptions.py)
(the constant is set to `None`), so building a prompt for them raises `NotImplementedError`.
Activate one by porting the description (see step 3 below).

## Adding a new domain in 4 steps

Suppose you want to add a `rovers` domain with 10 instances.

### 1. Drop the PDDL files

```
src/data/rovers/
├── domain.pddl              # or rovers_domain.pddl
├── instance-01.pddl
├── instance-02.pddl
└── ...                      # any number of instances
```

### 2. Register the alias in `config.yml`

```yaml
domains:
  available: [..., rovers]   # required so --domain rovers is accepted
  active:    [..., rovers]   # optional: include in default batch runs
```

### 3. Add a natural-language description

Edit [`src/prompts/descriptions.py`](../prompts/descriptions.py):

```python
ROVERS_DESCRIPTION = """ROVERS PLANNING TASK:

The domain has the following types: ...
The predicates are: ...
The actions are: ...
"""

DOMAIN_DESCRIPTIONS = {
    ...,
    "rovers": ROVERS_DESCRIPTION,
}
```

Use the existing `BLOCKSWORLD_DESCRIPTION` / `CITYCAR_DESCRIPTION` / `TETRIS_DESCRIPTION`
constants in the same file as templates. The description goes verbatim into both the
baseline and the CoT prompts — exact wording matters; see [`src/prompts/compose.py`](../prompts/compose.py)
for how it is composed.

> **Skipping this step is the most common reason a new domain "doesn't run."**
> Without a description (or with `None`), `compose.build_problem_prompt(...)` raises
> `NotImplementedError` on the first instance.

### 4. Generate `REFERENCE_PLANS.csv` (optional, recommended)

```bash
python scripts/verify/validate_instances.py --domains rovers
```

This runs [pyperplan](https://github.com/aibasel/pyperplan) on every instance and writes
a per-instance optimal-or-near-optimal plan length. The analysis notebook uses this as
a difficulty x-axis (Plot 12 / Plot 13 / Plot 15 in `notebooks/results_analysis.ipynb`).

**`:functions` warning.** If your domain uses numeric fluents (PDDL `:functions`),
pyperplan can't parse it and you'll see `parse-error: ...` in the CSV. The pipeline
still runs — the analysis notebook falls back to *empirical-consensus difficulty*
(Plot 14: per-instance solve rate across all model × condition cells) for those domains.
This is what `citycar` and `tetris` use.

### Smoke-test the wiring

Before launching a real run, verify the whole pipeline (file discovery → prompt build →
fake plan → validator → metrics) end-to-end with the stub model:

```bash
python src/main.py --domain rovers --condition baseline --model stub --iterations 1
```

If this finishes without `NotImplementedError` and writes `src/results/stub/rovers/baseline/`,
you're ready to launch a real model.

## What breaks gracefully vs loudly

| Missing piece | Symptom | Pipeline behavior |
|---|---|---|
| Description in `descriptions.py` | `NotImplementedError` from `compose.build_problem_prompt` | **Hard fail** at first prompt build. Add the description. |
| Domain not in `config.yml` `available` | argparse rejects `--domain <name>` | **Hard fail** at CLI parse. Add to `available`. |
| Domain file (`domain.pddl` / `*_domain.pddl`) | "domain file not found" warning | Domain silently skipped in batch mode. |
| Problem instance files | "no problem files detected" warning | Domain silently skipped. |
| `REFERENCE_PLANS.csv` | none (file simply absent) | Analysis notebook drops the difficulty plots for that domain; no crash. |
